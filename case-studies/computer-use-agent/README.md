## Step 1: Clarify Requirements & Frame the ML/AI Objective

**The actual objective.** Given a task described in natural language (e.g., "book this flight," "fill in this expense report," "find the invoice total on this vendor's portal and enter it into our accounting software") and a target piece of software, the agent has to complete that task by operating the software's actual graphical interface — the same interface a human operator would use — rather than through any purpose-built programmatic interface to that software. Concretely, per Anthropic's own confirmed description, the agent is given the ability to **"direct Claude to use computers the way people do—by looking at a screen, moving a cursor, clicking buttons, and typing text"** (source-confirmed, direct quote). The model is not handed a bespoke set of task-specific functions for the target software; Anthropic is explicit that the opposite design choice was deliberate: **"Instead of making specific tools to help Claude complete individual tasks, we're teaching it general computer skills"** (source-confirmed, direct quote) — one general-purpose "look at the screen and act" capability, reusable across any software with a visual interface, rather than one hand-written integration per application.

**What counts as ground truth / success.** Three distinct bars, from loosest to strictest:
1. **Task completion, as judged by the environment's own final state** — e.g., a form field in a real application now contains the correct value, a file was actually created, a flight was actually booked. This is the only bar that matters to an end user, and it's also the hardest to check automatically, since "did the real external system end up in the right state" generally requires either a scripted check against that system or human inspection.
2. **Benchmark-style, execution-based grading** — Step 6 covers this in full via the **OSWorld** benchmark, defined there in a Sidebar; the short version is that a task is scored by running an automated check against the actual resulting state of a real virtual-machine environment, not by a human or LLM judging whether the transcript "looks right."
3. **Per-action grounding correctness** — whether each individual simulated click, keystroke, or scroll actually did what the model intended it to do (defined in full as its own Sidebar in Step 3, since it's a genuinely new concept this repo has no existing home for). This is a necessary condition for #1, not a replacement for it: every action in a task can be correctly grounded and the task can still fail for a reason that has nothing to do with the GUI interaction (a wrong plan, a misunderstood instruction) — the same distinction Lesson 1's Concept A1 already draws generally between a model executing an action correctly and a model deciding on the *right* action in the first place.

**Explicitly out of scope:** fine-tuning or training the underlying vision-language model; any claim about exactly how Claude's own internal visual-grounding mechanism works (undisclosed, and this document does not speculate about model internals); a general RPA (robotic process automation) tool survey; the detailed mechanics of prompt-injection defense (Lesson 8's F1) or sandbox isolation (Lesson 8's F2), referenced below but not re-derived.

**Trade-offs considered.** Framing the objective as "operate the same GUI a human would" instead of "call a purpose-built API for this task" is not a default choice — it's a choice this capstone's whole point (Step 4) is to show is *usually the worse one, when a usable alternative exists*. Scoping the primary ground-truth bar to "benchmark-style execution-based grading" (OSWorld, #2 above) rather than "did the real production system end up correct" (#1) buys a reproducible, automatable signal — the same trade-off capstone #13 already made explicit for SWE-bench resolve rate versus a human-reviewed merge — at the same cost: a benchmark score is a narrower, cheaper-to-compute proxy for the thing a real deployment actually needs, which is real task completion against real, arbitrary software the benchmark's own fixed task set never saw.

## Step 2: Back-of-Envelope Constraints

Lesson 7's Concept 4 defines the five-step back-of-envelope method (state assumptions, decompose, compute with units, sanity-check the order of magnitude, name the most sensitive assumption) specifically so it isn't re-derived here. Applied directly:

**Step 1 — state assumptions explicitly.** Everything in this box is **(illustrative)** except where marked **(confirmed)**:
- **Screen resolution:** 1024×768 pixels — **XGA**, short for "Extended Graphics Array," a 4:3-aspect-ratio display resolution standard. This is **(confirmed)** as Anthropic's own recommended target: the reference implementation's own code comment states directly, *"sizes above XGA/WXGA are not recommended"* (source-confirmed, direct quote from `computer.py`), naming XGA (1024×768) and **WXGA** — short for "Wide XGA," 1280×800, 16:10 — as its two preferred scaling targets, alongside a third, **FWXGA** — short for "Full Wide XGA," 1366×768, ~16:9 — also defined in the same file.
- **Tokens per screenshot:** "roughly 1,000–1,800 input tokens each" — **(confirmed)**, a direct quote from Anthropic's current API documentation (not the 2024 announcement, which publishes no token-cost figure at all; dated separately per this document's Confidence note). This document uses the range's midpoint, **1,400 tokens/screenshot**, for the calculation below.
- **Conversation/history text tokens per round-trip:** 800 tokens **(illustrative)** — the system prompt, the task instruction, and the running action history the model needs re-sent each turn (per the agent-loop mechanics in Step 4).
- **Output tokens per round-trip:** 150 tokens **(illustrative)** — a short statement of what the model observed plus one action request; smaller than capstone #13's 300-output-token coding-agent round-trip, since a single GUI action (e.g., "click at (512, 340)") is a terser decision than a shell command or code edit.
- **Round-trips for one moderate task:** 24 **(illustrative)** — chosen to represent a task like filling a multi-field web form spread across a few screens, where Anthropic's own documented practice (Step 4) is to take a fresh screenshot after essentially every action, not just at the start.
- **Pricing:** $3/1M input tokens, $15/1M output tokens — the same **(illustrative)** anchor Lessons 7 and 8 and capstones #6, #7, and #13 already reuse, kept here for direct comparability rather than inventing a new figure.
- **Settle delay between an action and the next screenshot:** 500 ms — **(illustrative, but the underlying design pattern is confirmed)**: Anthropic's own reference implementation includes a code comment reading, verbatim, *"# delay to let things settle before taking a screenshot"* (source-confirmed) immediately before it captures the next frame; this document's 500 ms figure is the order of magnitude Anthropic's own current documentation separately recommends for its own `click_and_wait` helper (which the fetched page describes as sleeping 0.5 seconds) — the design practice is confirmed, the exact duration used here is this document's own illustrative choice matched to that order of magnitude.

**Step 2 — decompose:**
```
input_tokens_per_rt   = image_tokens_per_screenshot + history_text_tokens_per_rt
total_input_tokens    = round_trips × input_tokens_per_rt
total_output_tokens   = round_trips × output_tokens_per_rt
token_cost_per_task   = (total_input_tokens / 1,000,000) × input_price
                      + (total_output_tokens / 1,000,000) × output_price

latency_per_step      = screenshot_capture + encode_and_upload + model_inference
                      + action_execution + settle_delay
total_task_latency    = round_trips × latency_per_step
```

**Step 3 — compute step by step, carrying units.**

Token cost:
```
input_tokens_per_rt  = 1,400 + 800                     = 2,200 tokens
total_input_tokens   = 24 round-trips × 2,200          = 52,800 tokens  = 0.0528M
total_output_tokens  = 24 round-trips × 150            =  3,600 tokens  = 0.0036M

token_cost_per_task  = 0.0528 × $3  +  0.0036 × $15
                     = $0.1584  +  $0.0540
                     = $0.2124   ≈  $0.21 per task
```

Latency:
```
screenshot_capture    =  100 ms   (illustrative)
encode_and_upload     =  150 ms   (illustrative)
model_inference       = 2,000 ms  (illustrative — the single largest term)
action_execution      =   50 ms   (illustrative)
settle_delay          =  500 ms   (illustrative duration; confirmed design pattern)
                       --------
latency_per_step      = 2,800 ms  (2.8 seconds)

total_task_latency    = 24 round-trips × 2.8 s  =  67.2 seconds
```

**Comparing against a direct-API equivalent of the same logical task.** If the target software exposed a real API for this same operation, the equivalent task might take roughly 2 structured API calls — illustrative, e.g. one call to read current state, one to submit — at a much smaller 300 input / 50 output tokens each (a single structured request/response pair, not an image-laden conversation turn):
```
direct_api_input_tokens  = 2 × 300 = 600 tokens   = 0.0006M
direct_api_output_tokens = 2 × 50  = 100 tokens   = 0.0001M

direct_api_cost  = 0.0006 × $3  +  0.0001 × $15  =  $0.0018 + $0.0015  =  $0.0033

cost_ratio    = $0.2124 / $0.0033  ≈  64x
round_trip_ratio = 24 / 2 = 12x
```
At roughly 300–800 ms per direct API call (ordinary network-plus-processing latency, not an image-laden model inference), the direct-API version of this same task completes in on the order of 1–2 seconds total, versus the screenshot loop's 67.2 seconds — a **latency ratio in the same rough order of magnitude as the cost ratio**: dividing 67.2 seconds by this estimate's own "1–2 seconds total" figure gives a latency ratio of roughly **33.6x–67.2x**, a range that does bracket the independently-computed 64x cost ratio even though neither number was derived from the other. This is itself a useful sanity check: two independently-derived ratios (cost and latency) landing in the same broad, double-digit-to-double-digit ballpark — not a 2x difference, and not a 1,000x one — is a sign neither number is off by an order of magnitude in either direction, the same cross-check discipline capstone #13's own Step 2 applies to its fleet-sizing math.

**Step 4 — sanity-check the order of magnitude.** 67.2 seconds for a 24-step GUI task is a plausible order of magnitude for "a human filling out a short multi-screen form while being deliberate about it," not an obviously-wrong figure in either direction (not 0.67 seconds, not 672 seconds). It's also directly comparable to a number this repo has already established: Lesson 6's Concept 4 cites AWS ALB's documented 60-second default idle timeout for a synchronous connection. **A single moderate, 24-step computer-use task already exceeds that default timeout** — the direct implication for Step 5's serving architecture below.

**Step 5 — name the assumption the answer is most sensitive to.** **Model inference time per round-trip (2,000 ms)** is both the largest single term in the latency chain (71% of the 2,800 ms step total) and the one this document has the least real grounding for — Anthropic's 2024 announcement publishes no latency figures for computer use specifically (confirmed absence: a direct fetch of the announcement page, prompted explicitly for any latency claim, returned none). If inference time per round-trip is actually closer to 4,000 ms — plausible once the running action history (Step 3's `encode_and_upload`/history context) has grown over several turns — the per-step latency rises to 4,800 ms and the 24-step task total rises to 115.2 seconds, nearly double this estimate and almost twice AWS ALB's 60-second default timeout rather than just barely over it. That's the number worth measuring first in a real deployment, exactly as capstone #13's own Step 2 names its round-trip-count assumption as its own most sensitive, least-grounded figure.

**Trade-offs considered.** Choosing a 24-step task as the illustrative anchor keeps both the cost and latency math in a relatable range, but a real task distribution has a long tail — a multi-page checkout flow or a multi-app workflow could easily run 100+ steps, at which point Step 2's own $0.21/task and 67.2-second figures scale roughly linearly (ignoring the context-growth effect the Step 5 sensitivity note already flags), making this an increasingly expensive and slow way to accomplish something a direct API could do in a handful of calls — which is exactly the gap Step 4 below has to justify crossing at all. Using a flat 1,400-token screenshot estimate for every round-trip is also a simplification: Anthropic's own current documentation recommends pruning older screenshots from a long-running conversation (keeping 20 or fewer images per request) specifically because they otherwise accumulate — meaning, like capstone #13's own flat per-round-trip token estimate, this document's $0.21 figure should be read as a conservative floor for a short task and an underestimate for a long one, not a ceiling in either case.

## Step 3: Data / Knowledge Pipeline

**What the agent actually perceives at each step — and how it differs from every other agent architecture this repo has covered so far.** Capstone #13's coding agent perceives structured, textual context: file contents, shell output, test results — all of it already machine-readable, no visual interpretation required. Capstone #12's customer-support agents perceive structured per-customer records and retrieved policy text (Lesson 1, Concepts C1–C4). This capstone's agent perceives exactly one thing at every step: **a raw screenshot — a bitmap image of whatever is currently displayed on the target screen** — plus the running history of its own prior actions and the task instruction it started with. Nothing about the screen's content arrives pre-parsed into a button's name, a field's label, or a form's current value; the model has to derive all of that itself from pixels, the same way a human looking at the screen would, which is the direct, structural reason this architecture needs its own concept (action grounding, defined below) that a JSON-in/JSON-out tool call never needs.

**How a screenshot gets encoded for the model — real mechanics, not a black box.** Per Anthropic's own reference implementation **(source-confirmed)**, the screen is captured "at physical resolution" and then resized to a scaled coordinate frame before being sent to the model, specifically because — per that same file's own docstring, source-confirmed — "this is the coordinate frame the model emits coordinates in; it differs from the physical display whenever scaling applies." Concretely, the model is shown (and emits click coordinates in) the *scaled* frame, and the application has to map those coordinates back onto the *physical* screen before actually executing the click — a real, confirmed source of potential error if that mapping is off (e.g. on a high-DPI display, where one physical pixel doesn't correspond one-to-one to one logical pixel). Anthropic's own documented guidance generalizes this: on a Retina-class display with a 2x device pixel ratio, either the captured screenshot must be downscaled by 2x before being sent, or the model's returned coordinates must be halved before being executed — two different places to put the same correction, but it has to go somewhere, or every click lands in the wrong place by a consistent, predictable factor.

**Sidebar — Action grounding.** *(First appearance in this repo of this specific concept. It's genuinely AI/agent-native — not core infra Lessons 3–7 curate down to, and not already covered by Lesson 1's Groups A–E either — so it gets the full inline Sidebar treatment plus a glossary entry, rather than a lesson link that doesn't exist.)*
- **Why?** Lesson 1's Concept D3 (tool use/function calling, referenced not re-derived) already defines how a model requests an action: "a structured request to call one of those functions with specific argument values, which the surrounding application then actually executes and returns the result of." For a conventional tool call (e.g., `propose_refund(customer_id, amount)`, capstone #12's own example), the *argument values themselves* are exactly what the model means — there's no separate step where "the right customer_id" might silently differ from "the customer_id the model actually sent." A GUI action is structurally different: the model doesn't name *what* it's clicking (a semantic target, "the Submit button"), it names *where* — a pixel coordinate — and that coordinate is only correct if it happens to land on the actual, current, on-screen location of the element the model intended. Those two things (intended target, actual coordinate) can diverge for reasons that have nothing to do with whether the model's underlying plan was right.
- **What?** **Action grounding** is the process — and the failure mode when it goes wrong — of translating a model's intended action on a graphical interface (e.g., "click the Submit button") into the correct concrete low-level input (the exact pixel coordinates of that button on the *current* screen) such that executing that low-level input actually produces the intended effect. An **action-grounding error** is any case where the model's plan or reasoning was correct, but the concrete action it emitted — the coordinate, the scroll amount, the exact key sequence — did not actually correspond to the element or effect it intended, so the action "succeeds" mechanically (the click registers, no error is thrown) while still being the wrong action. This is a closely related phenomenon to what OSWorld's own authors call **"GUI grounding"** (confirmed from that paper's own stated finding that the best-performing model of its 2024 evaluation was "primarily struggling with GUI grounding and operational knowledge," per the search-confirmed summary of that paper) — this document treats "action grounding" (this capstone's own chosen term) and "GUI grounding" (OSWorld's own term) as naming the same underlying challenge from two sources, not as two different things, while being explicit that this equivalence is this document's own reasoned inference, not a claim either source states in those words.
- **How?** Applied here directly: a scrollbar or a dropdown menu is a harder target to ground correctly than a large, uniquely-colored button, because its clickable region is small, its visual appearance can be ambiguous, and (per Anthropic's own current documentation, confirmed, though dated separately from the 2024 announcement per this document's Confidence note) "some UI elements (such as dropdowns and scrollbars) might be tricky for Claude to manipulate using mouse movements" — a direct, sourced instance of the Sidebar's own definition. The mitigation that same current documentation recommends is instructive precisely because it sidesteps grounding rather than solving it: try a keyboard shortcut (e.g., arrow keys to move a dropdown's selection) instead of a mouse click, because a keyboard action has no coordinate to get wrong in the first place.

**A real action-request example, showing exactly what "the model names a coordinate, not a semantic target" means concretely** — the field names inside this call are Anthropic's own confirmed action-call shape, from the reference implementation's own API-facing schema (the tagging note just below this block spells out exactly which parts of it are source-confirmed versus illustrative):
```json
{
  "type": "tool_use",
  "id": "toolu_01A2bCdeFGhij3klmNOp4qrS",
  "name": "computer",
  "input": {
    "action": "left_click",
    "coordinate": [512, 340]
  }
}
```
There is no field anywhere in this call naming "the Submit button," "the email field," or any other semantic identity — only `[512, 340]`, a raw pixel coordinate the surrounding application executes literally, exactly as given, with no way to check on its own whether that coordinate actually lands on the element the model's own reasoning (sent separately, as text, in the same turn) said it intended to click.

*(Tagging note, since this block mixes source-confirmed and illustrative content more finely than most quotes in this document: the `action`/`coordinate` field names are source-confirmed directly from `computer.py`'s method signature; the outer `tool_use`/`id`/`name` envelope is Anthropic's general Messages API tool-use block format, not something `computer.py` itself defines; and the specific `id` string and the `[512, 340]` coordinate value are this document's own illustrative placeholders, invented to show the shape, not pulled from any real transcript.)*

**Trade-offs considered.** Sending the model a downscaled screenshot (rather than the full physical resolution) reduces both the image's token cost (Step 2) and the risk of exceeding the model's documented image-size limits, but it also throws away real pixel detail — exactly the mechanism Anthropic's own current documentation names, in its click-troubleshooting table, as one cause when "clicks land in the right area but miss the target": that "detail was lost downscaling a 4K+ source" (source-confirmed, direct quote, scoped in that table specifically to a high-resolution source screen, not stated as a general claim about downscaling) — so the scaling factor is itself a direct trade-off between cost/latency and grounding accuracy, not a free optimization. Choosing to represent the screen as a single flat image (rather than, say, a structured accessibility tree of named UI elements, which some other GUI-automation approaches use instead) is what makes this approach general-purpose across arbitrary software with no per-application integration work — Anthropic's own stated goal — but it's also the direct cause of the action-grounding problem this Sidebar defines; a structured-element representation would make "click the Submit button" a semantic, not a coordinate-based, action, trading away generality (it requires the target software to expose such a structure at all, which most legacy GUIs don't) for grounding reliability.

## Step 4: Model/Agent Core Design — the Screenshot-Reasoning-Action Loop as a Variant of ReAct, and the Explicit Trade-off Against a Direct-API Agent

**Placing this loop inside Lesson 1's own control-flow vocabulary, rather than treating it as something new.** Lesson 1's Concept D2 already defines **ReAct** in full: "a control-flow pattern where the model alternates, in a loop, between writing out a short reasoning step..., taking an action..., observing that action's result, and then reasoning again about what to do next — continuing until it decides it has enough information to give a final answer." Anthropic's own confirmed description of the computer-use loop maps onto this definition almost exactly, and its own documentation (current, not the 2024 announcement, dated separately per this document's Confidence note) names the loop directly: "the repetition of... Claude responding with a tool use request and your application responding to Claude with the results of evaluating that request" is, in that documentation's own words, "referred to as the 'agent loop.'" This document treats the computer-use loop as **a special case of ReAct, not a different pattern** — the same Thought → Action → Observation → repeat shape Lesson 1 already names, specialized in exactly two ways that matter for this capstone's own teaching point:

1. **The observation is always a raw screenshot, never a structured result.** A conventional ReAct loop's "observation" step, applied to a weather-lookup tool, returns something already machine-readable — `{"temperature_f": 72}` — that the model can use directly with no further interpretation. This loop's observation is a bitmap the model has to visually re-parse from scratch on every single turn, which is the direct structural cause of the action-grounding concept (Step 3) a plain function-calling ReAct loop never needs at all: a weather tool's returned temperature can't be "the wrong temperature because the reading was imprecise," but a screenshot-derived click coordinate absolutely can be the wrong coordinate despite registering as a mechanically successful click.
2. **The action space is one small, fixed, general-purpose vocabulary, not many task-specific functions.** Lesson 1's Concept D3 (tool use/function calling, referenced not re-derived) describes the ordinary shape of an agent's toolset: a set of named functions, each wrapping a meaningful, semantically-scoped operation (capstone #12's `propose_refund(customer_id, amount)` is exactly this shape). This loop instead exposes Step 3's 10-action vocabulary (`left_click`, `type`, `key`, `screenshot`, …) as the *entire* toolset, regardless of what software is being operated — the same function-calling mechanism D3 already defines, deliberately applied to a uniform set of GUI primitives instead of a rich, task-specific function library. This is the concrete form of Anthropic's own confirmed design choice (Step 1): one general tool, reusable across arbitrary software, instead of one bespoke integration per application.

**The explicit trade-off: why ever choose this slower, costlier, more error-prone loop over a direct-API agent?** Step 2's own numbers already show the direct-API alternative wins decisively on cost (≈64x cheaper) and latency (roughly 34x–67x faster, by Step 2's own recomputed range) for the same logical task, whenever a usable API actually exists. So the real design question this capstone exists to answer isn't "which is better in general" — it's "when is the slower, costlier option the *only* option." Three real reasons, not hypothetical ones:

1. **No API exists at all.** The overwhelming majority of installed software — legacy desktop applications, a decade-old internal line-of-business tool, a vendor's admin console that was only ever built with a human operator in mind — has no programmatic interface whatsoever. For this software, "direct-API agent" isn't a faster alternative sitting on the table; it's not an alternative at all.
2. **An API exists, but doesn't expose what's needed.** A SaaS vendor's public API frequently covers only its most common integration use cases, while a specific settings toggle, a report-export option, or a less-common workflow step is only reachable through the vendor's own web UI — the API surface and the GUI surface of the same product are not guaranteed to be equivalent, and often aren't.
3. **The task is inherently about arbitrary, not-known-in-advance software.** A browser agent asked to "find the cheapest flight across these three airline sites" or "check whether this specific government portal shows my application as received" is being asked to operate software the agent's own builders never integrated with and, for a sufficiently general browser agent, never will — writing a bespoke scraper or API client per target site doesn't scale to "arbitrary website," which is exactly the generality Anthropic's own "general computer skills" framing (Step 1) is built to buy.

**Why the loop's "observe" half is load-bearing, not decorative — the compounding math, applied to grounding error specifically.** Suppose a 24-step task (Step 2's own illustrative anchor) is executed with no per-step verification at all — the model commits to and blindly executes all 24 actions with no fresh screenshot in between to catch a mis-grounded click before the next action builds on top of it. Even at a generous 95% per-action grounding accuracy (the same illustrative 95% per-step reliability figure capstone #13's own Step 4 uses, for direct comparability):
```
P(all 24 actions correctly grounded, no correction) = 0.95^24 ≈ 0.292   →   roughly a 29.2% chance of a fully clean run
```
Nearly 71% of the time, at least one of 24 actions in an uncorrected sequence would be mis-grounded — not because the model's plan was wrong, but purely from the accumulated chance of at least one coordinate missing its intended target along the way. This is **this document's own illustrative sanity check, not a derivation of any disclosed Anthropic figure** — Anthropic publishes no per-action grounding accuracy number — but it's the concrete reason Anthropic's own documented recommendation (current docs, confirmed, dated separately) to take a fresh screenshot and let the model check the result after essentially every action isn't an optional nicety: without that observation step, a 24-step task's odds of completing with zero uncaught mis-grounded actions are worse than a coin flip. The loop's observation half is exactly ReAct's own "observe the result before deciding the next action" — Lesson 1's own definition, applied here specifically to catch an action-grounding error (Step 3) before the next action compounds on top of it, the same structural role capstone #13's own "fix mistakes" observation step plays for a general planning error, just specialized to this architecture's own characteristic failure mode.

**Trade-offs considered.** Choosing a screenshot-perceiving, coordinate-emitting action space over a direct-API or structured-accessibility-tree alternative buys genuine generality — one capability that works (imperfectly) across any software with a visual interface, with zero per-application integration work — at the direct, measured cost Step 2 already quantified (≈64x the token cost, roughly 34x–67x the latency of an equivalent direct-API task) and the structural cost this Step quantifies (a per-action grounding failure mode a structured tool call never has). Anthropic's own confirmed, remarkably candid framing of this trade-off is itself worth quoting directly rather than paraphrasing: **"At this stage, it is still experimental—at times cumbersome and error-prone"** and **"Claude's current ability to use computers is imperfect"** (both source-confirmed, direct quotes) — not a vendor claiming a finished, reliable product, but a vendor naming the exact trade-off this Step argues for: the loop is chosen only when no cheaper, more reliable alternative exists, never as a default.

## Step 5: Serving Architecture

**The latency chain per step, made concrete as an actual request/response flow.** Step 2's own decomposition — `screenshot_capture → encode_and_upload → model_inference → action_execution → settle_delay`, repeating once per round-trip — is the serving-level reality underneath this capstone's loop, and it maps onto a real request flow:

```
Orchestrator process
   │
   │ 1. capture current screen  (screenshot_capture, ~100ms illustrative)
   ▼
Encode image, build request (running history + task instruction + new screenshot)
   │  (encode_and_upload, ~150ms illustrative)
   ▼
Claude API  ── model_inference (~2,000ms illustrative; Step 2's most sensitive term) ──►
   │  returns one or more tool_use blocks (Step 3's action schema)
   ▼
Orchestrator executes the requested action(s) against the real display/browser
   │  (action_execution, ~50ms illustrative)
   ▼
settle_delay (~500ms illustrative duration; confirmed design pattern — "delay to
   let things settle before taking a screenshot")
   │
   └──► loop back to step 1, until the model returns no further action requests
```

**Why this can't be one synchronous request — delivering on Step 2's own finding, exactly the way capstone #13's Step 5 delivered on Lesson 6's forward reference.** Step 2 already computed a 67.2-second total latency for a 24-step task, against Lesson 6's Concept 4 own cited figure: AWS ALB's documented 60-second default idle timeout for a synchronous connection. A single moderate computer-use task already exceeds that default — not a multi-hour edge case the way capstone #13's 90-minute coding sessions are, but enough to rule out a plain synchronous request/response for anything beyond the shortest tasks. The architecture this capstone needs is therefore the same shape capstone #13's Step 5 already built out for exactly this reason, reused here rather than reinvented: a REST-shaped submit call that returns immediately with a task ID, a task queue (Lesson 6, Concept 1) running the actual screenshot-reasoning-action loop as a background job, and a separate progress channel the caller polls or subscribes to — the same three-part decomposition Lesson 6's own Concept 4 defines in full and capstone #13's Step 5 already applies, not re-derived a third time here.

**The sandboxing requirement — and why it's not optional for this specific architecture.** Executing simulated mouse/keyboard input against a real display means the orchestrator needs an actual, running display environment to act against — a virtual display (e.g., an X virtual framebuffer) if the target is a desktop environment, or a real, controllable browser instance if the target is a web application — and Lesson 8's Concept 2 (sandboxing agent execution, referenced not re-derived) applies to that environment at least as strongly as it does to capstone #13's shell/editor/browser sandbox: whatever the model's actions can reach on that display is exactly this architecture's blast radius (Lesson 7, Concept 1, referenced not re-derived), and because this agent's whole mode of operation is "act like a human operator," a successful attack or a bad decision has the same reach a human operator logged into that same session would have.

**Why prompt injection is an unusually acute risk for this specific architecture — and why Lesson 8's F1 applies here more directly than almost anywhere else in this repo.** Lesson 8's Concept 1 already defines indirect prompt injection in full: "the injected instruction is planted in *third-party content* that the model reads as part of doing its job... a web page it fetched, a file it was asked to summarize, or a tool's returned output." A computer-use agent's *only* input, every single step, is a rendered view of whatever is currently on screen — if that screen is displaying a malicious web page, or any attacker-controlled content at all, the injected instruction isn't buried in one retrieved document among many (capstone #9's RAG case) or in one tool's returned output (capstone #13's browser-tool case) — it's the *entirety* of what the model perceives at that step, with no separate "trusted system prompt" channel visually distinguishing it from legitimate on-screen content the way a delimited, labeled RAG chunk can be (Lesson 8's own first mitigation layer). Anthropic's own current documentation states this risk directly and starkly (confirmed, dated separately from the 2024 announcement per this document's Confidence note): "Claude will follow commands found in content even when they conflict with your instructions" — the same underlying risk Lesson 8's Concept 1 already names generally, confirmed here by Anthropic's own documentation as a risk specific to exactly this architecture, not a hypothetical.

**Caching and optimization.** Lesson 1's Concept B4 (prompt caching, referenced not re-derived) applies to this loop's *fixed* content — the system prompt and the tool/action-space definition (Step 3's JSON schema), which are identical on every single round-trip of a session — but explicitly does **not** apply to the one piece of content that changes every single turn: the screenshot itself. This is a direct, structural limit on how much of this loop's own cost (Step 2) caching can realistically claw back: the 800 illustrative history-text tokens per round-trip are a real candidate for prefix caching (most of that history is identical to the previous turn's, plus one new increment), but the dominant cost term — Step 2's own 1,400-token screenshot — is, by definition, new, unique pixel content every single round-trip and cannot be served from a cache the way a repeated system prompt can.

**Trade-offs considered.** Routing the loop through a task queue (rather than a synchronous request) adds real infrastructure — a queue, a worker pool, a separate progress-polling endpoint — that a short, sub-60-second task doesn't strictly need, but per Step 2's own sensitivity finding (model inference time could plausibly double), relying on "this particular task will probably stay under the timeout" is a fragile bet to build a serving architecture on, which is exactly why capstone #13 made the same choice for its own, much longer tasks. Running the target display inside a dedicated, isolated sandbox (rather than, say, giving the agent a session on a shared, persistent desktop environment) costs real provisioning overhead per task — spinning up a fresh virtual display or browser instance — but bounds the injection/blast-radius risk above to that one task's own sandbox, rather than letting a successfully-injected action reach a shared environment's other, unrelated sessions or credentials.

## Step 6: Evaluation, Monitoring, and Iteration

**Offline evaluation — OSWorld, with Anthropic's own confirmed headline figures.**

**Sidebar — OSWorld.** *(First appearance in this repo of this benchmark; glossary entry added below.)*
- **Why?** Exactly the same reason capstone #13's own Sidebar gives for SWE-bench: a model's own transcript of "I clicked the right button" is not an objective way to know whether a computer-use task actually succeeded — something has to check the real, resulting state of a real environment, automatically and reproducibly.
- **What?** **OSWorld** is a benchmark and accompanying execution environment, from Xie et al.'s NeurIPS 2024 paper, that evaluates an agent's ability to complete real, open-ended computer tasks — spanning real desktop and web applications across actual Ubuntu, Windows, and macOS environments — by giving the agent free-form mouse/keyboard control and checking the task's completion via an automated, execution-based evaluation script run against the environment's actual final state (file contents, application state), not a human or LLM judgment of the transcript. A **"screenshot-only"** evaluation category, specifically, restricts the agent's perception to exactly this capstone's own architecture — screenshots, with no additional structured accessibility information about the screen's contents — as opposed to a setup that also hands the agent a parsed, structured representation of on-screen elements.
- **How?** Applied to this capstone directly: Anthropic's own 2024 announcement reports, as a direct quote, confirmed by fetching the page — **"On OSWorld, which evaluates AI models' ability to use computers like people do, Claude 3.5 Sonnet scored 14.9% in the screenshot-only category, notably better than the next-best AI system's score of 7.8%. When afforded more steps to complete the task, Claude scored 22.0%."** Read against OSWorld's own benchmark paper, this figure is genuinely low in absolute terms — a different, earlier evaluation of OSWorld reported humans completing over 72% of its task set, against the best contemporary model's roughly 12% at that time — which is the concrete form of Step 4's own "still experimental... cumbersome and error-prone" framing: even the model generating the headline-setting 14.9%/22.0% score was, by the benchmark's own absolute terms, resolving well under a quarter of its real-world computer-task set.

**Why this isn't the only evidence worth reporting.** Anthropic's same announcement also reports a confirmed, directly quoted coding-specific result — **"it improves performance on SWE-bench Verified from 33.4% to 49.0%"** — which is worth naming here specifically because it's a *different* kind of improvement than the OSWorld figure: SWE-bench Verified measures the underlying model's general reasoning/coding capability uplift (the same benchmark family capstone #13's Sidebar already defines), not this capstone's own screenshot-and-action loop specifically, and the two shouldn't be conflated as if they measured the same thing just because they were announced together.

**Action-grounding error monitoring — the metric this capstone's own architecture needs that neither OSWorld's pass/fail score nor a general uptime dashboard gives you.** A task that ultimately fails OSWorld's own grading doesn't by itself tell you *why* — whether the model's plan was wrong, or the plan was right but a specific action was mis-grounded (Step 3). A real deployment needs this broken apart: logging, for a sampled subset of completed tasks, whether each individual action's *intended* target (recoverable from the model's own stated reasoning in that turn) matched its *actual* on-screen effect (checkable via the very next screenshot, which is already captured as part of the loop per Step 4's own observation step) — the concrete, measurable form of this Sidebar's own definition, analogous to capstone #12's own validator catch-rate in that both are a *rate at which a specific, named failure mode is caught*, just applied here to action grounding instead of validator-blocked bad actions.

**The feedback loop.** Tasks that fail OSWorld-style grading, or that a production deployment flags via the action-grounding monitoring above, are exactly the input worth routing back into Step 3's own resolution/scaling choices (a UI element type that consistently mis-grounds might mean the downscaling factor needs adjusting for that class of target) and Step 1's own task-instruction framing (a consistently misunderstood instruction is a prompting problem, not a grounding one) — the same "route real production failures back into the thing that needs fixing" shape capstones #9, #12, and #13 already establish, applied here to grounding failures and benchmark-style task failures specifically.

**Failure modes — Anthropic's own disclosed caveats, not downplayed.** Beyond the "experimental... cumbersome and error-prone" framing already quoted in Step 4, Anthropic's own current documentation (confirmed, dated separately per this document's Confidence note) names two further, specific failure patterns directly relevant to production monitoring: Claude "sometimes assumes outcomes of its actions without explicitly checking their results" — the exact failure Step 4's own observe-and-correct argument exists to reduce, not eliminate — and certain UI elements (dropdowns, scrollbars) are disclosed as disproportionately hard to ground correctly via mouse movement alone. A production deployment's own monitoring should track error rates broken out by UI-element type for exactly this reason, the same "isolate which specific category is driving the error rate, not just a single blended number" discipline capstone #12's own per-specialist-domain error tracking already applies to a different kind of agent.

**Trade-offs considered.** Sampling a subset of completed tasks for human action-grounding review (rather than reviewing every task) scales to real production volume but, like every sampled-audit approach this repo has already named (capstone #5/#11's stratified auditing, capstone #12's validator-audit sampling), trades completeness for cost — a grounding failure mode affecting a rare but real UI pattern could go unnoticed longer than it would under full review. Leaning primarily on Anthropic's own disclosed "low-risk tasks" recommendation (quoted in Step 4) as a deployment gate — i.e., restricting this architecture's early production use to tasks where a mis-grounded action is cheap to detect and reverse, rather than ones involving irreversible real-world consequences — is the safest rollout path given both this architecture's own structural error mode (Step 3) and Anthropic's own stated caveats, but it also means this architecture's highest-value use cases (irreversible, consequential actions on legacy software with no API — Step 4's own strongest justification for using it at all) are exactly the ones a cautious rollout defers longest, a real tension this document doesn't resolve for a specific deployment, only names.
