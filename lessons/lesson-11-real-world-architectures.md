# Lesson 11: Real-World Architectures and Further Reading

**Time:** 45-60 minutes
**Tool(s):** Conceptual survey — no single tool; this lesson is a map of real tools, companies, and blogs, not a hands-on walkthrough

## Purpose of this lesson

Every other lesson in this course (1-9) and every `case-studies/` capstone teaches a pattern and roots it in one real, documented case. This lesson does something different: it's the AI-world analog of `system-design-primer`'s own "Real world architectures," "Company architectures," and "Company engineering blogs" sections — proof the patterns taught here show up *beyond* the 14 capstones that got full six-step treatment. It has almost no content of its own; its job is pointing back at Lessons 1-10 and the capstone catalog, and pointing *forward* to real tools and blogs you can go read.

Lesson 11 is a **survey lesson, not a teaching lesson**. It does not follow the Concept/Why/What/How template the rest of this repo uses. Instead, N1-N3 below are link-and-one-liner **tables**, and this lesson's depth-bar substitute — in place of a numeric calculation — is that **every single table row names which Lesson or capstone it reinforces**. A row that didn't would be a dangling fact, not reinforcement (see N4). Where a real primary or credible source could not be confirmed for an entry, that's flagged explicitly in the row rather than papered over, following the same sourcing discipline the `case-studies/` capstones already use.

## N1. AI infrastructure building blocks

The analog of `system-design-primer`'s MapReduce/Bigtable/GFS/Chubby/Kafka/Zookeeper table: the real, named infrastructure pieces sitting underneath the patterns Lessons 1-10 teach conceptually. Every tool below was verified as real (not reconstructed from memory) via web search at the time this lesson was written.

### Model-serving engines

| Tool | One-line description | Reinforces |
|---|---|---|
| **vLLM** | An open-source LLM inference/serving library, originally from UC Berkeley's Sky Computing Lab, built around **PagedAttention** — storing each request's KV cache in fixed-size, non-contiguous memory blocks instead of one large contiguous allocation — plus continuous batching, quantization, and an OpenAI-compatible API server. | Lesson 1's B1 (batching, KV cache) and B4 (KV-cache reuse); this is the literal mechanism capstone #10 (`case-studies/llm-inference-serving`) is built around — the glossary's PagedAttention/paged-block entries come directly from this tool's own paper. |
| **Triton Inference Server** (NVIDIA) | Open-source model-serving software that deploys models from many frameworks at once (TensorRT, PyTorch, ONNX, OpenVINO, Python) behind one HTTP/gRPC/C-API interface, with a per-model scheduler and real-time/batched/streaming request support. | Lesson 1's B1 (hosted vs. self-hosted serving, batching) — a general-purpose alternative to vLLM for the same serving problem capstone #10 addresses, and a real example of the model-routing/gateway pattern (Lesson 1 B3) operating one layer lower, in front of the model backends themselves rather than in front of providers. |
| **TensorRT-LLM** (NVIDIA) | An open-source toolkit that gives LLMs an easy-to-use Python API and compiles them into optimized TensorRT engines for NVIDIA GPUs, with in-flight batching, paged KV caching, and FP8/FP4/INT4/INT8 quantization; ships a Triton backend for production serving. | Lesson 1's B1 (batching, quantization) directly; its own paged-KV-caching design is a second real-world implementation of the same PagedAttention-style idea capstone #10 teaches via vLLM — a case of two different vendors converging on the same fix for the same bottleneck resource. |
| **Ray Serve** | A scalable, framework-agnostic Python model-serving library built on the Ray distributed-computing framework, suited to multi-model composition and pipelines (not just single-model serving), with fractional-GPU scheduling, request batching, and native Kubernetes support. | Lesson 1's B1 (model serving fundamentals) and Lesson 7's M1 (monolith vs. microservices, since Ray Serve's whole pitch is composing several models/business logic as one deployable graph) — a second real serving engine for the same problem capstone #10 covers from the PagedAttention angle. |

### Vector/retrieval infrastructure

| Tool | One-line description | Reinforces |
|---|---|---|
| **Pinecone** | A fully managed, cloud-native vector database with a simple API — store an embedding plus metadata, query for nearest neighbors — with no index infrastructure for the user to operate themselves. | Lesson 1's C2 (vector databases) and Lesson 5's K2 (NoSQL types — why a vector DB is architecturally closest to a KV/wide-column hybrid, not a fifth category); directly the retrieval infrastructure capstone #9 (`case-studies/rag-contextual-retrieval`) assumes underneath its contextual-chunk index. |
| **Weaviate** | An open-source vector database, written in Go, that stores both objects and vectors together so vector similarity search can be combined with structured filtering, with native horizontal scaling, multi-tenancy, and replication. | Same mapping as Pinecone: Lesson 1's C2 and Lesson 5's K2/K4 bridge, and capstone #9's retrieval layer — shown here as a self-hostable alternative to a managed vector DB, the same hosted-vs-self-hosted fork Lesson 1's B1 names for model serving. |
| **Milvus** | An open-source, cloud-native vector database (Apache 2.0, under LF AI & Data) built for embedding similarity search at scale, with storage and compute separated and all components stateless for elastic scaling. | Lesson 1's C2 and Lesson 5's K2/K4; its storage/compute separation is a direct real-world instance of Lesson 3's scalability Concept (I1) applied to retrieval infrastructure specifically rather than to LLM-token throughput. |
| **FAISS** | A library from Meta AI (originally Facebook AI Research, 2017) for efficient similarity search and clustering of dense vectors, in C++ with full Python/NumPy wrappers, with GPU-accelerated implementations for the largest indexes. | Lesson 1's C2 (vector databases) broadly — FAISS supports both approximate-nearest-neighbor indexes (e.g. HNSW, the ANN problem C2 introduces) and exact/brute-force ones, including binary indexes (e.g. `IndexBinaryFlat`) built for already-binarized vectors. The real tie to capstone #1 (`case-studies/visual-search`) runs through that second, exact mode, not the first: Pinterest's own design (Step 5) deliberately avoids ANN approximation altogether, binarizing its embeddings specifically so a brute-force, *exact* Hamming-distance scan per shard stays cheap — and FAISS's exact/binary-index support is the real-world mechanism matching that design, not FAISS's HNSW/ANN side. |
| **pgvector** | An open-source PostgreSQL extension that adds a vector data type plus exact and approximate (HNSW, IVFFlat) nearest-neighbor search directly inside Postgres, so vector search gets ACID compliance, replication, and JOINs for free. | Lesson 5's K1 (RDBMS scaling) and K2 (NoSQL types) simultaneously — it's the one tool on this list that is literally the classic-vs-AI-native bridge Lesson 5's K4 Concept argues for, by putting the AI-native pattern (vector search) inside the classic infrastructure (an RDBMS) rather than beside it. |

### Agent/workflow orchestration

| Tool | One-line description | Reinforces |
|---|---|---|
| **LangGraph** | A low-level orchestration framework/runtime (from the LangChain team, usable independently of LangChain) for building long-running, stateful agents as a graph of nodes and edges — supporting cycles, conditional branching, durable execution, and human-in-the-loop checkpoints; used in production by companies including Klarna and Uber. | Lesson 1's D2 (control-flow patterns: ReAct, plan-and-execute, reflection — LangGraph is a real runtime for implementing exactly these loop shapes) and D5 (multi-agent orchestration); directly reinforces capstone #12 (multi-agent customer-support platform) and capstone #13 (autonomous coding agent's plan-then-execute loop). |
| **Temporal** | An open-source durable-execution platform: workflows are written as ordinary code, but Temporal persists their state and event history so a workflow can resume after a crash, retry, or deployment, surviving runs that span minutes to months. | Lesson 1's E3 (state/checkpointing across multi-step runs) directly — Temporal is a real, general-purpose implementation of the exact checkpointing problem E3 describes abstractly — and Lesson 6's L4 (why a long-running agentic task can't be served as one synchronous REST request); the clearest real-world infrastructure match for capstone #13's multi-hour autonomous coding sessions. |

### ML-ops infrastructure

| Tool | One-line description | Reinforces |
|---|---|---|
| **MLflow** | An open-source platform for the complete ML lifecycle, with four components: Tracking (log and compare experiment runs), Projects (reproducible run packaging), Models (a packaging format deployable across serving platforms), and a Model Registry (a central, versioned model store). | Lesson 9's G4 (prompt/model versioning and rollback) — MLflow's Model Registry is the classic-ML-era tool doing exactly what G4 teaches for prompts; also reinforces the Step 6 (evaluation/monitoring/iteration) pattern every Track 1 capstone follows, concretely for capstones like #2 (CTR prediction) and #7 (Uber ETA) that retrain and re-version models continuously. |
| **Feast** | An open-source feature store: it manages an offline store (for historical feature extraction used in training) and a low-latency online store plus feature server (for serving the same features to production models), generating point-in-time-correct feature sets to prevent future values leaking into training data. | Lesson 5's K1/K2 (data layer: it sits directly on top of existing databases rather than replacing them) and the "data/knowledge pipeline" Step 3 of the 6-step method — the real infrastructure answer to capstone #6's "hundreds of features" (PYMK) and capstone #2's large online-learning feature set needing to be identical between training and serving. |
| **Kubeflow** | "The Machine Learning Toolkit for Kubernetes" — a set of Kubernetes-native components covering the ML lifecycle: Pipelines (portable workflow orchestration), Notebooks, a Trainer for distributed fine-tuning/training, Katib for hyperparameter tuning, and KServe for production model serving. | Lesson 7's M1/M2 (microservices and service discovery, since Kubeflow is literally "run this ML lifecycle as a set of Kubernetes services") and Lesson 10's H1 (scaling patterns for agentic workloads — the same Kubernetes HorizontalPodAutoscaler mechanism Lesson 10's own Hands-On Walkthrough snippet uses). |

### LLM observability/eval infrastructure

| Tool | One-line description | Reinforces |
|---|---|---|
| **LangSmith** | LangChain's platform for tracing, debugging, and evaluating LLM applications: it records every model call, tool use, and agent step in a run, lets you pinpoint exactly where a failure happened, and supports both offline evaluation on curated datasets and online scoring of live traffic. | Lesson 9's G2 (offline evaluation — golden datasets, regression suites) and G3 (online observability — tracing an agent run); this is the real, named tool resolving capstone #9's own forward reference to "Lesson 9, G1-G2" for generation-quality evaluation. |

| **Arize** | An AI observability and LLM-evaluation platform: it indexes training, validation, and production data in one central store so ML teams can detect where a model's problems emerge and investigate why, covering both classic ML models and LLM/agent applications; its open-source counterpart is Phoenix. | Lesson 9's G3 (online observability — tracing an agent run, latency/cost dashboards) directly, and G1 (why you can't unit-test an LLM the normal way, hence needing an observability layer at all); concretely the kind of infrastructure capstone #13's own trace/span storage-cost calculation (Lesson 9, Concept 3) is modeling. |

## N4. How to read N1-N3

Don't read the three tables above as fourteen new homework assignments. The instruction `system-design-primer` gives for its own equivalent sections applies unchanged: **don't focus on the nitty-gritty implementation details of any one entry.** You are not expected to come away from this lesson knowing exactly how Triton's C API differs from Ray Serve's scheduler, or how Spotify's synthetic-voice pipeline is wired together. That depth belongs to the primary sources themselves, if and when you need it for a specific project — not to this lesson.

What you *should* do with every entry above is ask three questions:

1. **What shared principle or recurring technology does this entry represent?** Look across rows, not down one row at a time. Four different companies (vLLM, Triton, TensorRT-LLM, and — per capstone #10's own sourcing — Character.AI) all converge on paged, non-contiguous KV-cache memory management as the fix for the same bottleneck. Five different vector-infrastructure tools (Pinecone, Weaviate, Milvus, FAISS, pgvector) all solve the same approximate-nearest-neighbor problem with different trade-offs (managed vs. self-hosted, standalone vs. bolted onto an existing RDBMS). Seeing the repetition *is* the point — evidence the pattern is real, not an artifact of one company's taste.
2. **What problem does this entry solve, and where does that approach break down?** Every tool and company above was chosen to solve something specific, under specific constraints. Temporal's durable-execution model assumes your workflow code is written deterministically enough to replay — that assumption breaks down for a workflow with genuine non-determinism baked into its logic (not just an LLM call's sampling, but actual branching on wall-clock time or random I/O). Midjourney's row above is a case where the "approach" can't even be named with confidence, because no primary source describes it — that absence is itself informative: it tells you this company has chosen not to publish its internals, which you should notice rather than paper over with a confident-sounding guess.
3. **Which Lesson (1-9) or capstone does this entry's core trick actually map back to?** Every row in N1-N3 above already states this explicitly — that mapping is this lesson's whole depth-bar substitute. If you can't make that connection for a new tool or company you encounter later, after finishing this repo, that's a signal: **an entry that doesn't connect back to something already taught is a dangling fact, not reinforcement.** It might still be worth knowing. But don't mistake "I recognize this company's name" for "I understand the system design principle underneath it" unless you can name which Lesson or capstone's pattern it's an instance of.

This is also the exact self-check Checkpoint 11 asks you to perform, on three entries of your own choosing, rather than against a fixed answer key — because for a survey lesson like this one, there isn't a single right answer to "what did Perplexity build," only whether you can trace it back to something this repo already taught you.
